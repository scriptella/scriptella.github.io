CSV import benchmarks

One million rows, two databases, and a reproducible comparison of Scriptella 1.6, handwritten JDBC, and csvsql.

Batched Scriptella imported the fixture in 14.79 seconds on PostgreSQL and 9.52 seconds on MariaDB on a local development machine. Handwritten JDBC was faster; csvsql’s tested direct-import workflow took about 9–10 minutes. PostgreSQL COPY is included as a separate native reference.

These are exploratory results for one workload. The benchmark repository contains the implementation, raw measurements, dependency metadata, and full reports.

Scriptella’s elapsed-time advantage over csvsql was 37.7× on PostgreSQL and 62.7× on MariaDB, calculated as csvsql duration divided by Scriptella duration. Chunking and JDBC batching use different mechanisms; matching the row-group size does not make the import paths equivalent.

The host was an Intel Core i9-9980HK Mac with 32 GiB RAM, running Docker through x86_64 Colima with 4 CPUs and 6 GiB RAM. See the local result notes and all individual measurements.

What was measured

  • Workload: 1,000,000 deterministic CSV rows with an integer ID, two strings, an exact decimal amount, and a timestamp. No nulls, transformations, indexes, or primary keys.
  • Versions: Scriptella 1.6, Java 17, csvsql 2.2.0, PostgreSQL 17.11, and MariaDB 11.8.8. Database durability and JDBC driver options retain normal defaults.
  • Transactions: one transaction and one commit per import, including unbatched cases. Scriptella and JDBC use identical driver settings and explicit typed conversions.
  • Timing: fresh client process startup through exit after commit and cleanup. Fixture generation, database startup, warmup, table reset, and verification are excluded.
  • Checks: all cases pass a 2,001-row smoke import. Each measured import is checked independently for row count and first, middle, and last values before its timing is recorded.

An untimed 20,000-row import precedes each measured case. It primes file and database caches, but the measured Java process starts a fresh JVM, so its JIT is not warmed. Case order is fixed. Two local runs and one CI run support a directional comparison, without establishing precise uncertainty or universal speedups.

csvsql uses its documented direct-import path with default type inference and --chunk-size 1000. Its in-memory table preparation differs from Scriptella’s streaming CSV path. COPY streams the fixture through PostgreSQL’s native import interface; it is a database-specific reference, not a performance ceiling.

Coarse first-run MariaDB process resident high-water observations were approximately 188 MiB for batched Scriptella, 146 MiB for batched JDBC, and 895 MiB for csvsql. One-second polling can miss late peaks; these are whole-process observations, not Java heap or total database/container memory. Sampling and manual progress checks occurred during parts of the first local run; the second had no sampler. See the memory collection notes.

Run it yourself

The host needs Git, a Docker-compatible runtime, and Docker Compose. The benchmark image supplies Java, Python, Scriptella, and the database clients.

git clone https://github.com/scriptella/scriptella-benchmarks.git
cd scriptella-benchmarks
ENVIRONMENT_ID=my-machine-docker \
ENVIRONMENT_DESCRIPTION='Describe CPU and Docker runtime' \
SCRIPTELLA_VERSION=1.6 docker compose up --build \
  --abort-on-container-exit --exit-code-from benchmark

The local runs took about 33–35 minutes each. Results and diagnostics are saved under results/. After inspection, remove the experiment’s stopped containers and database volumes with docker compose down --volumes.

For smoke-only runs, aggregation, and the full measurement contract, see the benchmark instructions.
